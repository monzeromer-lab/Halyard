RUNTIME

Routing rules

A routing rule decides which build or function answers a request. Rules live in your repository, ship inside the artifact, and are evaluated at the edge before anything of yours runs.

Stable since v9

Edge only

2 ms budget

The match object

Every rule is { match, target }. The match object is a conjunction: each key you set must be satisfied, and keys you omit are not consulted. A rule with an empty match is the fallback and must be last.

import { defineRoutes } from 'halyard' export default defineRoutes([ // pin the beta cohort to a known build { match: { cookie: { ht_beta: '1' } }, build: '8f2c41' }, // EU traffic prefers fra1, then falls through { match: { geo: { country: ['DE', 'FR', 'NL'] } }, region: 'fra1' }, { match: { path: '/api/*' }, fn: 'api', timeout: 10_000 }, { match: { path: '/*' }, build: 'current' }, ])

Rules are part of the build

Changing a rule produces a new artifact and a new hash. That is deliberate: it means a rollback restores the routing that shipped with the code, not whatever the dashboard happened to say at the time.

Evaluation order

Rules are read top to bottom and the first match answers. There is no scoring and no specificity system to learn: if two rules could both match, the one written first wins. The CLI refuses a deploy where a later rule is unreachable.

  1. Cookie and header rules, because they are the narrowest.

  2. Geo rules, which only choose a preferred region.

  3. Path rules that send traffic to a function.

  4. The fallback, which is always a build hash.

Targets

A rule sends the request to exactly one of three things: a build, an edge fn, or a preferred region. A region target does not answer the request; it only reorders which region is asked first, and the next rule still applies.

Weighted rules must sum to 100

If you split traffic with weight, every rule in that group has to add up to exactly 100. A group that sums to 99 or 101 fails the deploy with HL-4021 rather than silently sending the remainder to the fallback.

Computed rules

When a header comparison is not enough, match.fn takes a pure function that receives the request and returns a boolean. It runs inside a 2 ms budget on the same isolate that will serve the request, so it has no network and no KV access. Throwing counts as no match and is recorded on the trace.

Rule parameters

Routing rule parameters, their types and defaults
Key Type Default Notes
match.path string | string[] — Glob against the pathname. A trailing /* matches any depth; /*.js matches one segment.
match.header Record<string, string> — All listed headers must match. Values are compared case-insensitively after trimming.
match.cookie Record<string, string> — Exact cookie value match. Absent cookies never match, including against an empty string.
match.geo { country?, region?, asn? } — Resolved at the edge from the client address. Falls through when the lookup is unavailable.
match.fn (req) => boolean — A pure function evaluated in under 2 ms. Throwing counts as no match and is logged.
build string current A build hash, or current. Pinning a hash freezes this rule until you change it.
fn string — Name of an edge function in this project. Mutually exclusive with build.
timeout number 10000 Milliseconds before the request is cut and a 504 is returned to the client.
weight number 100 Share of matching traffic, 0 to 100. Weighted rules must sum to 100 or the deploy is refused.

What goes wrong

Three errors account for most refused deploys. Each one is reported with the rule index and the line in your source, before anything is uploaded.

HL-4019

A rule after the fallback can never match.

HL-4021

Weighted rules in a group do not sum to 100.

HL-4033

match.fn exceeded the 2 ms budget during the deploy check.
