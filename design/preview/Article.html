No releases of that kind

Nothing in the last ten releases carried that tag.

Until this release, a routing rule was something you changed in a dashboard, and it took effect on whatever build happened to be live. That is a reasonable design right up to the first incident, when the rollback restores the code and leaves the routing exactly as broken as it was.

From v9.4 the rules are a file in your repository. They are compiled into the artifact, signed with it, and evaluated at the edge before any of your code runs. A rollback restores both, because there is only one thing to restore.

What changed

Three things, and the third is the one that will cost you an afternoon if you skip it.1

  • Rules are read from routes.halyard.ts at build time and embedded in the artifact.
  • The dashboard rule editor is now read-only, and shows which file and line a rule came from.
  • Weighted splits must sum to exactly 100. Groups that do not are refused at deploy with HL-4021.

Migrating

Your existing rules are exported to routes.halyard.ts the first time you deploy on v9.4. Nothing is deleted, and v2 routes.json is still read and translated on import.2

What we are doing next

Rules can currently only choose between builds, functions and preferred regions. The next release opens the same evaluation to cache keys, so a rule can decide what a response is stored under rather than only who answers it. If you are relying on a header-derived cache key today, that work is for you.

FOOTNOTES

1. The afternoon is the weighted split check. Every group we saw in the beta that summed to 99 had been that way for months without anyone noticing the missing 1%.

2. Translation is lossy in exactly one place: a v2 rule with no target inherited the project default. On import it is written out with an explicit build hash.
